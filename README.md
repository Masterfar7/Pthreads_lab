## 1. Задача 1: Множество Мандельброта
### Описание алгоритма
- Проверяется принадлежность комплексных чисел $c = x + iy$ множеству Мандельброта по формуле $z_{n+1} = z_n^2 + c$, $z_0 = 0$.
- Условие выхода за границу: $|z|^2 = x^2 + y^2 > 4$ при $n \le 1000$.
- Параллелизация: сетка комплексной плоскости разбивается циклически по строкам между потоками (`rank, rank + nthreads, ...`).
- Синхронизация: потоки накапливают найденные точки в локальный буфер и периодически сбрасывают под мьютексом в общий массив, минимизируя накладные расходы на блокировки.
- Результат выгружается в формат `mandelbrot.csv` ($x, y$).

### Формат запуска:
```bash
./program <nthreads> <npoints>
# Пример: ./program 4 5000
```

### Замеры времени (для 5000 точек):
| Количество потоков | Время (сек) |
|---|---|
| 1 поток | 0.0381 с 
| 2 потока | 0.0210 с 
| 4 потока | 0.0125 с 
| 8 потоков | 0.0078 с

## 2. Задача 2: Задача N тел (гравитация)
### Описание алгоритма
- Моделируется движение $N$ гравитационно взаимодействующих тел в трехмерном пространстве по закону всемирного тяготения Ньютона.
- Учтен 3-й закон Ньютона (`F_pq = -F_qp`).
- Для численного решения системы дифференциальных уравнений применен метод Эйлера 1-го порядка
- Стандартный `pthread_barrier_t` отсутствует в macOS, поэтому реализован собственный барьер на мьютексе и условной переменной. Он содержит счётчик пришедших потоков и счётчик «поколений». Поколение нужно, чтобы ложное пробуждение не выпустило поток раньше времени и чтобы быстрый поток не перепутал соседние барьеры.
- Вычисления ведутся в трёх измерениях, так как входной файл содержит три координаты и три компоненты скорости. В CSV выводятся только x и y, как требует формат вывода. Если во входных данных z = 0 и v\_z = 0, задача сводится к плоской.
- Смягчение сил (добавка к расстоянию, защищающая от деления на ноль) не используется. При совпадении положений двух тел происходит деление на ноль, как и в исходной формуле.

### Пояснения к коду

| Элемент | Назначение |
| --- | --- |
| `barrier_t`, `barrier_init`, `barrier_wait`, `barrier_destroy` | собственный барьер на `pthread_mutex_t` и `pthread_cond_t` |
| `m, x, y, z, vx, vy, vz` | массивы параметров тел длины N, общие для всех потоков |
| `fx, fy, fz` | локальные массивы сил: `fx[t][i]` — вклад потока t в силу на тело i |
| `worker` | функция потока: все шаги по времени, две фазы и два барьера на шаг |
| `write_row` | запись строки CSV (только x и y), вызывается потоком 0 |
| `main` | разбор аргументов, чтение входного файла, выделение памяти, запуск и ожидание потоков, замер времени |

Обработка аргументов командной строки:

`./nbody tend input_file [nthreads] [dt] [output.csv]`

- `tend` и `input_file` обязательны;
- `nthreads` — число потоков, по умолчанию 4 (если больше N, уменьшается до N);
- `dt` — шаг по времени, по умолчанию `tend/1000`;
- `output.csv` — выходной файл, по умолчанию вывод идёт в stdout.


### Сборка и запуск

```bash
gcc -O2 -o nbody nbody.c -lpthread -lm
./nbody tend input_file [nthreads] [dt] [output.csv]
```

Пример замера

```bash
./nbody 10 input_big.txt 4 0.01 /dev/null
```

Формат вывода: CSV, строка `t,x1,y1,x2,y2,...,xn,yn` на каждый момент времени.

### Оборудование и ПО

| Параметр | Значение |
|---|---|
| Процессор | Apple M1 |
| Ядра | 8 физических и 8 логических (4 производительных + 4 энергоэффективных) |
| Память | 16 ГБ |
| Сборка | `gcc -O2 -o nbody nbody.c -lpthread -lm` |


### Условия замера

- Вход: `input_big.txt`, 2000 тел.
- `tend = 10`, `dt = 0.01` (1000 шагов).
- Вывод направлялся в `/dev/null`.
- Время измерялось внутри программы через `gettimeofday` (макрос `GET_TIME` из `timer.h`). В замер входят расчёт и форматирование вывода, чтение входного файла не входит.
- Каждая конфигурация запускалась 3 раза. Для сравнения используется минимальное время (оно меньше подвержено влиянию фоновых процессов), среднее приведено для справки.

### Результаты

Итоги (ускорение и эффективность считаются по минимальному времени):

| Потоков p | T_min, с | T_среднее, с | Ускорение S(p) = T_min(1)/T_min(p) | Эффективность E(p) = S(p)/p |
|---|---|---|---|---|
| 1 | 8.006 | 8.046 | 1.00 | 1.00 |
| 2 | 4.442 | 4.533 | 1.80 | 0.90 |
| 4 | 2.640 | 2.667 | 3.03 | 0.76 |

### Выводы

- Программа масштабируется: на 2 потоках ускорение около 1.8 раза, на 4 потоках около 3.0 раза.
- Эффективность падает с ростом числа потоков (с 0.90 до 0.76). Вероятные причины: два барьера на каждом из 1000 шагов, редукция локальных массивов сил (её объём растёт с числом потоков) и последовательные части, которые выполняет только поток 0 (форматирование строк вывода). Эти причины не проверялись отдельными замерами.
- Разброс между запусками небольшой: 1.2% на 1 потоке, 2.8% на 4 потоках. На 2 потоках он больше (6%): первый запуск (4.709 с) заметно медленнее двух других (около 4.44 с), поэтому среднее для 2 потоков выше минимума. Использование минимума снижает влияние таких выбросов.

### Примечание о корректности

Результаты при разном числе потоков совпадают с точностью до ошибок округления, а не побитово: порядок суммирования сил зависит от числа потоков, а сложение чисел с плавающей точкой не ассоциативно. На тесте из 5 тел (звезда и 4 планеты на круговых орбитах, `tend = 100`, `dt = 0.001`) максимальная разница координат между запусками на 1 и 4 потоках составила около 1e-8 м (последняя выводимая цифра).

## 3. Задача 3: Собственная реализация rwlock

### Описание реализации

Структура содержит:

- две условные переменные: `read_cond` (на ней спят читатели) и `write_cond` (на ней спят писатели);
- счётчик `readers`: сколько потоков читают прямо сейчас;
- счётчики `readers_waiting` и `writers_waiting`: сколько читателей и писателей ждут блокировку;
- `mutex`, защищающий все остальные поля;
- флаг `writer_active`: держит ли блокировку писатель.

Реализован **приоритет писателей** (writers-preference): новый читатель не допускается, пока в очереди есть хотя бы один писатель. Это защищает писателей от голодания при постоянном потоке читателей. Обратная сторона: при непрерывном потоке записи читатели могут ждать дольше.

### Описание алгоритма

Правила входа:

- **чтение (`my_rwlock_rdlock`)**: поток ждёт на `read_cond`, пока `writer_active == 1` или `writers_waiting > 0`. После этого он увеличивает `readers`. Читатели не мешают друг другу, поэтому читать могут сколько угодно потоков одновременно;
- **запись (`my_rwlock_wrlock`)**: поток ждёт на `write_cond`, пока `writer_active == 1` или `readers > 0`. После этого он ставит `writer_active = 1`.

Выход (`my_rwlock_unlock`) одна функция для обоих режимов. Если `writer_active == 1`, значит, выходит писатель, и флаг сбрасывается. Иначе выходит читатель, и `readers` уменьшается. Затем:

- если читающих нет и есть ждущие писатели, будится один писатель (`pthread_cond_signal`);
- иначе, если ждущих писателей нет, а ждущие читатели есть, будятся все читатели (`pthread_cond_broadcast`), так как они могут войти одновременно.

Каждый вызов `pthread_cond_wait` стоит внутри цикла `while`: возможны ложные пробуждения, и к моменту возврата из ожидания состояние может измениться.

Мьютекс `mutex` удерживается только на время проверки и правки счётчиков. Само чтение или изменение списка выполняется после возврата из `rdlock`/`wrlock`, уже без внутреннего мьютекса. Поэтому читатели действительно работают параллельно.

### Пояснения к коду

| Элемент | Назначение |
| --- | --- |
| `my_rwlock_t` (`my_rwlock.h`) | структура блокировки: мьютекс, две условные переменные, три счётчика, флаг писателя |
| `my_rwlock_init`, `my_rwlock_destroy` | инициализация и уничтожение; все счётчики и флаг обнуляются |
| `my_rwlock_rdlock` | захват на чтение с приоритетом писателей |
| `my_rwlock_wrlock` | захват на запись (эксклюзивный) |
| `my_rwlock_unlock` | освобождение любого режима; решает, кого разбудить |
| `pth_ll_rwl.c` | односвязный отсортированный список; `Member` вызывается под блокировкой чтения, `Insert` и `Delete` под блокировкой записи; одна блокировка на весь список |

### Сборка и запуск

Исходный тест `pth_ll_rwl.c` собирается в двух вариантах из одного исходника: с библиотечным `pthread_rwlock_t` и с `my_rwlock_t`. Остальной код (список, генератор `my_rand`, распределение операций) в обоих вариантах одинаков.

```bash
./pth_std 8 1000 1000000 0.8 0.1
```

Аргументы: число потоков, число ключей, вставляемых в список до старта потоков, общее число операций, доля поиска, доля вставок (доля удалений равна остатку, то есть 0.1). Версия с собственной блокировкой запускалась с теми же аргументами.

### Оборудование и ПО

| Параметр | Значение |
|---|---|
| Процессор | Intel Core Ultra 5 125H (18 логических потоков) |
| ОС | Windows 11 + WSL 2 (Alpine Linux x86_64; в Alpine стандартная библиотека C это musl, а не glibc) |
| Компилятор | GCC 13.2.1 (`-O3 -Wall -pthread`) |

### Условия замера

- Время измерялось внутри программы макросом `GET_TIME` из `timer.h` (`gettimeofday`) вокруг создания потоков и ожидания их завершения. Заполнение списка в замер не входит.
- Нагрузка: 80% поиска, 10% вставок, 10% удалений. Генератор псевдослучайных чисел задаётся фиксированными начальными значениями, поэтому в обеих версиях потоки выполняют одну и ту же последовательность операций (счётчики операций совпадают, см. ниже).
- Серия 1: 100 000 операций, 1, 2, 4 и 8 потоков. Число запусков на конфигурацию: 3
- Серия 2: 1 000 000 операций, 8 потоков. Число запусков на конфигурацию: 2

### Результаты

**Серия 1: 100 000 операций.**

| Число потоков | `pthread_rwlock_t`, с | `my_rwlock_t`, с | `my_rwlock_t` / `pthread_rwlock_t` |
|---|---|---|---|
| 1 | 1.15 | 1.18 | 1.026 |
| 2 | 1.58 | 1.62 | 1.025 |
| 4 | 1.91 | 2.05 | 1.073 |
| 8 | 2.45 | 2.60 | 1.061 |

На этом размере задачи собственная реализация медленнее библиотечной на 2.5–7.3%.

**Серия 2: 1 000 000 операций, 8 потоков.** Выполнено операций: всего 1 000 000 (поиск 799 652, вставка 99 921, удаление 100 427), в обеих версиях одинаково.

| Реализация | Запуск 1, с | Запуск 2, с | T_min, с |
|---|---|---|---|
| `pthread_rwlock_t` | 320.17 | 310.05 | 310.05 |
| `my_rwlock_t` | 200.54 | 205.01 | 200.54 |

- Отношение времён `T(pthread_rwlock_t) / T(my_rwlock_t)` по минимальному времени: 310.05 / 200.54 = 1.55. Собственная реализация быстрее примерно на 35%.
- Разброс между двумя запусками стандартной реализации 3.3%, то есть заметно меньше наблюдаемой разницы.

### Выводы

- Реализованная блокировка поддерживает семантику «один писатель или любое число читателей» и приоритет писателей.
- Знак разницы между реализациями зависит от размера задачи: при 100 000 операций собственная блокировка медленнее на 2.5–7.3%, при 1 000 000 операций на 8 потоках быстрее на 35%. При миллионе операций список вырастает: вставляются случайные ключи из большого диапазона (`MAX_KEY`), и почти все вставки успешны, а удаления почти всегда промахиваются. Обход длинного списка занимает много времени, и стоимость самой блокировки на этом фоне мала. Поэтому результат определяется скорее политикой планирования (кто и когда получает блокировку), чем скоростью примитивов.
- Возможные причины выигрыша собственной реализации (отдельными замерами не проверялись): отличие политики очереди от политики стандартной реализации в используемой libc (в Alpine это musl) и расхождение времени удержания блокировок писателями и читателями. Результат получен на одном запуске собственной версии и одной аппаратной конфигурации, поэтому вывод о преимуществе следует считать предварительным.
- В серии 1 время растёт с числом потоков у обеих реализаций, то есть ускорения нет. Вероятные причины: одна блокировка на весь список, исключительный доступ писателей (20% операций) и затраты на синхронизацию, сопоставимые с работой под блокировкой. Эти причины отдельными замерами не проверялись.

### Примечание о корректности

- Счётчики операций в обеих версиях совпадают (поиск 799 652, вставка 99 921, удаление 100 427), то есть потоки выполняют одну и ту же работу.
- Взаимное исключение проверено отдельным стресс-тестом `rwlock_stress_test.c`: 8 потоков по 200 000 операций (около 70% чтений и 30% записей), внутри критических секций считались активные читатели и писатели. Нарушений не обнаружено (`violations=0`), число записей совпало с ожидаемым.
- ThreadSanitizer на том же тесте предупреждений о гонках не выдал.
